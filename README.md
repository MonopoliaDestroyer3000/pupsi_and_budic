# Budget-aware openJiuwen agent

Агент для openJiuwen Challenge 2026. Решает набор файловых задач в пределах общего бюджета токенов. Запускается через `openjiuwen.core.runner.Runner` как реализация `BaseAgent`.

## Запуск

Требования: Docker, доступ к OpenAI-совместимому прокси и каталог задач.

```bash
docker build -t hack:latest .
docker run --rm \
  -e LLM_BASE_URL -e LLM_API_KEY -e BUDGET \
  -v "$TASKS:/data/tasks:rw" \
  --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --cpus 4 --memory 16g --pids-limit 512 \
  --workdir /app --entrypoint python hack:latest \
  /app/run_agent.py --tasks-dir /data/tasks
```

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `TASKS` | Путь к каталогу задач на хосте для монтирования | — |
| `LLM_BASE_URL` | Базовый URL прокси, включая `/v1` | — |
| `LLM_API_KEY` | Ключ прокси | — |
| `BUDGET` | Общий бюджет в эквивалентных выходных токенах | 100000 |
| `AGENT_CONCURRENCY` | Число параллельных сессий, от 1 до 5 | 3 |
| `TIME_LIMIT` | Время выполнения в секундах | 3450 |
| `AGENT_MODEL` | Модель первого прохода | qwen3.8-27b-noreason |
| `REASONING_MODEL` | Модель повторной попытки | qwen3.8-27b |

Бюджет читается при запуске; поддерживается любое конечное неотрицательное значение. Ключ передаётся только в заголовке запроса. Если `LLM_BASE_URL` или `LLM_API_KEY` не заданы, выполняется только детерминированный проход.

## Формат данных

Каталог каждой задачи содержит `task.json` с полями `task_id`, `task_type`, `instruction`, `reward` и необязательный подкаталог `workspace`. Другие поля метаданных не используются решателем и планировщиком.

После решения `answer.txt` атомарно сохраняется в каталоге задачи. При наличии `workspace` ответ также сохраняется в нём. Изменения исходников кодовых задач остаются в workspace. Файлы тестов не изменяются.

Параметр `--output-file` задаёт дополнительный JSON с ответами, расходом и событиями выполнения. Поддерживаются также `--output` и переменная `OUT`. Флаг `--resume` включает повторное использование сохранённых ответов с перепроверкой кодовых задач. Логи выводятся в stderr, итоговый JSON — в stdout.

## Решение и планирование

Первый проход не использует LLM:

- **math:** интерпретация последовательности операций над складским запасом с полным покрытием условий;
- **data_analysis:** CSV-агрегации с фильтрами по продукту, региону и месяцам;
- **search:** поиск в markdown-базе и переходы по связям employer/mentor;
- **coding:** AST-исправления стандартных функций с последующим запуском полного набора видимых unittest-тестов.

Неподдержанная формулировка передаётся модельному решателю. Отсутствие обязательных данных в распознанном шаблоне и противоречивые проверки служат признаками невыполнимости. Ошибочные отказы возможны при иной структуре данных.

Для остальных задач решается приближённая задача о рюкзаке: ожидаемая полезность равна `reward × P(success)`, ограничение — оставшийся бюджет. Портфель пересчитывается после завершения попыток. Порядок запуска определяется отношением полезности к ожидаемому расходу.

Начальные оценки расхода для math/search/data_analysis/coding составляют 850/1400/1800/3700 токенов. Оценка корректируется по размеру входа и сглаженным наблюдениям завершённых попыток. Повторные попытки получают пониженную вероятность успеха.

Модельный цикл использует JSON-действия `list`, `read`, `grep`, `python`, `write`, `test`, `answer`, `skip`. Контекст ограничен исходной задачей и последними взаимодействиями; число шагов — 7 для обычных задач и 10 для кодовых. Повторяющиеся действия без прогресса прерывают попытку. Кодовое решение принимается только после успешного выполнения неизменённых тестов; отсутствие тестов успехом не считается. При неудаче изменения откатываются.

## Учёт ресурсов

Стоимость вызова: `prompt_tokens / 10 + completion_tokens`. Вход учитывается полностью, без скидки за кеш. Reasoning, включённый в completion usage, не суммируется повторно; отдельные счётчики и `total_tokens` используются для восстановления расхода.

До вызова резервируются оценка входа по UTF-8 байтам и лимит выхода. Общая блокировка учитывает параллельные запросы. После ответа резерв заменяется фактическим usage. При отсутствующем или некорректном usage и ошибках транспорта списывается резерв. Это может завышать внутренний расход. Внешний жёсткий лимит обеспечивает прокси.

Модельные инструменты ограничены workspace. Вычислительный Python не предоставляет сеть, shell, запись файлов и произвольные импорты. На Linux ограничены память и размер вывода. Тесты запускаются отдельным процессом с очищенным окружением и ограничениями времени/вывода; окончательную изоляцию исполняемого кода обеспечивает контейнер.

Образ использует Python 3.12.10 и openJiuwen 0.1.19. В `requirements.txt` закреплена цепочка зависимостей используемых `BaseAgent` и `Runner`; неиспользуемые интеграции полного пакета не устанавливаются. Сборка включает проверку вызова агента. Локальные модели, веса и загрузка данных при запуске не используются.

## Проверки

```bash
python -m unittest discover -s tests -v
python tools/benchmark.py --synthetic --count 100 --seed 20261113 --output .work/benchmark.json
```

`tools/generate_training.py` создаёт воспроизводимый набор с заданной долей невыполнимых задач. `tools/benchmark.py` запускает агент на временной копии без оценочных меток, проверяет ответы независимым оценщиком, неизменность тестов и дополнительные синтетические coding-кейсы. Флаг `--with-framework` включает openJiuwen в бенчмарке; без него проверяется автономный решатель. CI выполняет тесты, сборку образа и прогон с ограничениями файловой системы.

Локальные результаты: 8/8 исходных примеров, 20/20 баллов, без вызовов LLM. На трёх сгенерированных наборах по 100 задач решены 240/240 выполнимых задач и пропущены 60/60 невыполнимых; неверных отправок нет. Наборы покрывают известные шаблоны и не оценивают качество на скрытом распределении. Интеграционный прогон через `qwen3.6-35b-a3b-noreason` решил задачу `17 × 23`: два вызова, 370 входных и 15 выходных токенов, итоговая стоимость 52.

Собранные локальные прогоны относятся к детерминированным траекториям; для интеграционного прогона зафиксирован суммарный usage. При указании `--output-file` модельная траектория сохраняется в событиях `llm_step`: задача, модель, инструмент, краткое наблюдение и расход. Ключи и тексты рассуждений не сохраняются.
